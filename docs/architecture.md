# compute-service: архитектура и решения подробно

Краткая версия — в [README](../README.md). Здесь: зачем каждое решение, как его
проверить руками и что показали нагрузочные тесты.

Распределённый сервис тяжёлых вычислений: FastAPI за Nginx, Redis во всех
ролях (кэш, rate limit, pub/sub, distributed lock) и горизонтальный скейлинг на
несколько backend-контейнеров. Задача одна и намеренно тяжёлая: N-е число Фибоначчи
**наивной рекурсией** (~φ^N вызовов), чтобы было что кэшировать, от чего защищаться
локом и что выносить в отдельные процессы.

## Архитектура

```
                         Интернет / браузер
                                 │  HTTPS :443  (HTTP :80 → 301 на HTTPS)
                                 ▼
┌────────────────────────── nginx ───────────────────────────┐
│ TLS termination · gzip · security-заголовки                │
│ limit_req (грубый слой rate limit)                         │
│   /            → статика с диска (backend не нужен)        │
│   /api/compute → upstream backend (least_conn), 20 r/m     │
│   /api/*       → upstream backend, мягкий лимит            │
│   /ws          → upstream backend_ws (Upgrade: websocket)  │
└───────────────┬───────────────────────────┬────────────────┘
                │ HTTP (внутренняя сеть)    │
      ┌─────────▼─────────┐       ┌─────────▼─────────┐
      │ backend реплика 1 │  ...  │ backend реплика N │   docker compose --scale backend=N
      │ gunicorn (мастер) │       │ gunicorn (мастер) │
      │  ├ uvicorn-воркер │       │  ├ uvicorn-воркер │   × WEB_CONCURRENCY
      │  │  event loop    │       │  │  event loop    │
      │  │  └ ProcessPool │       │  │  └ ProcessPool │   × COMPUTE_POOL_SIZE
      │  └ uvicorn-воркер │       │  └ uvicorn-воркер │     (тут считается fibonacci)
      └─────────┬─────────┘       └─────────┬─────────┘
                │   общий connection pool на воркер
                ▼                           ▼
┌─────────────────────────── Redis ──────────────────────────┐
│ compute:cache:<sha256>  кэш результатов, TTL 1 ч           │
│ compute:lock:<sha256>   distributed lock (SET NX EX)       │
│ ratelimit:compute:<ip>  5 вычислений/мин (INCR + EXPIRE)   │
│ concurrency:compute:<ip> вычислений с IP прямо сейчас      │
│ канал compute:results   Pub/Sub → живая лента у всех       │
│ канал compute:lock-released  Pub/Sub → будит ждущих лок    │
└────────────────────────────────────────────────────────────┘
```

Снаружи доступен **только nginx**. Порты backend и Redis не проброшены — поэтому
backend может доверять заголовку `X-Real-IP` (подделать его в обход nginx нельзя).

### Путь запроса `POST /api/compute {"input": N}`

1. **Порог на N** (Pydantic, `0..MAX_FIBONACCI_N`, по умолчанию 35) → 422. Первым
   делом и без Redis: +1 к N ≈ ×1.6 времени, +5 ≈ ×11, а уже запущенное в пуле
   процессов вычисление не отменить (`Future.cancel()` не работает для начатых
   задач). Защищаемся входом, а не таймаутом постфактум.
2. **Rate limit** в Redis: 5 запросов в минуту с IP → 429. Общий для всех реплик.
3. **Кэш**: результат детерминирован → если есть, отдаём сразу (`from_cache: true`).
4. **Distributed lock** (защита от cache stampede) — см. ниже.
5. **Защита от перегрузки** (только если реально считаем): одно вычисление на IP
   одновременно → 429. Если все процессы пула заняты — запрос **ждёт своей очереди
   на сервере** (FIFO, `asyncio.Semaphore`), а не получает отказ сразу. 503 с
   `Retry-After` — только если очередь переполнена (`BACKPRESSURE_FACTOR ×
   COMPUTE_POOL_SIZE` задач на воркер) или слот не освободился за
   `COMPUTE_QUEUE_WAIT_SECONDS`. Лок при любом отказе снимается сразу.
6. **Вычисление** в `ProcessPoolExecutor` через `run_in_executor`.
7. Результат → кэш → снятие лока → публикация в канал `compute:results`.

### Distributed lock — самое неочевидное место

Проблема: 5 одинаковых запросов пришли одновременно, в кэше пусто. Без защиты все
5 запустят одно и то же дорогое вычисление (cache stampede). `asyncio.Lock` не
поможет: реплик и воркеров много, у каждого своя память. Общая точка — Redis.

```
запрос ──► кэш? ──да──► ответ (from_cache)
            │нет
            ▼
   SET lock:<hash> <token> NX EX 120 ──OK──► кэш ещё раз? ──да──► ответ
            │занят                              │нет
            ▼                                   ▼
   спим до "лок снят" (или 1 с)           лимиты → вычисление → кэш
            ▼                                   │
   кэш? ──да──► ответ                           ▼ finally
            │нет                        снять лок (Lua: только свой token)
   лок ещё есть? ──нет──► снова SET NX  PUBLISH compute:lock-released <hash>
            │да
   прошло 60 с? ──да──► 504
```

- `NX` — атомарно: из любого числа одновременных SET успешен ровно один.
- `EX 120` — страховка на случай падения держателя; в разы больше худшего
  вычисления, иначе лок истечёт посреди работы.
- **Повторная проверка кэша после взятия лока**: иначе запрос, который промахнулся
  мимо кэша чуть раньше, возьмёт только что освобождённый лок и посчитает заново.
- **Снятие только своим токеном** через Lua-скрипт (атомарно): иначе запрос, чей
  лок истёк по TTL, удалил бы чужой лок.
- Если лок исчез без результата (держатель упал или получил 503), ждущий сам
  берёт лок, а не сидит до таймаута.
- **Ждущие не опрашивают Redis, а спят до уведомления.** Держатель после снятия
  лока делает `PUBLISH compute:lock-released <hash>`; в каждом воркере одна
  подписка будит всех местных ждущих этого лока (`asyncio.Event`). Раньше был опрос
  каждые 200 мс: 1000 ждущих — тысячи команд в секунду ради одного события и
  задержка до 200 мс. Раз в секунду ждущий всё же перепроверяет сам — страховка:
  Pub/Sub не гарантирует доставку, а убитый SIGKILL держатель ничего не опубликует
  (его лок истечёт по TTL).

#### Ожидание при нагрузке: сервер ждёт за клиента

Назвать клиенту точное время «когда сервер освободится» без очереди нельзя: место,
освободившееся в 12:00:01, может занять кто-то, пришедший в 12:00:00,9. Точное
время = резервирование места = очередь. Поэтому:

- **Основной путь — ожидание на сервере.** Вычисления короткие (порог N держит их
  около секунды), и подождать слот пару секунд на сервере лучше, чем отказать.
  Очередь честная (FIFO) и **ограниченная** по длине и времени — неограниченная
  очередь означала бы растущую без предела задержку и память.
- **Запасной путь — повтор на клиенте** (`static/app.js`), только при 503 и
  «ваше вычисление ещё идёт»: через `Retry-After` + случайная добавка, растущая
  с каждой попыткой (иначе все отказанные повторят одновременно — thundering herd).
  Максимум 5 попыток, есть кнопка «Отмена».
- **Минутный лимит (429 `rate_limit`) не повторяется автоматически** — до конца
  окна повтор получит тот же отказ. Кнопка показывает отсчёт «Можно снова через N с».

Чтобы клиент различал случаи, у ошибок есть поле `reason`: `rate_limit`, `ip_busy`,
`overloaded`, `queue_timeout`, `lock_timeout`, `redis_unavailable`.

#### Redis под нагрузкой и при сбое

- **`BlockingConnectionPool`**: когда все соединения пула заняты, запрос ждёт
  свободное (до `REDIS_POOL_TIMEOUT_SECONDS`), а не падает. Обычный `ConnectionPool`
  при исчерпании сразу бросает `MaxConnectionsError` — на тесте «1000 одинаковых
  запросов» это было 493 ответа 500.
- **Таймауты сокета** (5 с на команду, 2 с на соединение): зависший Redis не
  подвешивает запросы навсегда.
- **Redis недоступен → 503 `redis_unavailable` + `Retry-After`**, а не 500:
  это временная недоступность зависимости, повтор уместен. Воркер при этом
  стартует и без Redis, `/api/health` честно отвечает 503, подписка
  восстанавливается сама.

## Живая лента: Pub/Sub + WebSocket

Вычисление прошло на реплике A, а зритель подключён по WebSocket к реплике B.
A делает `PUBLISH compute:results`, а **каждый воркер каждой реплики** подписан на
канал (одна подписка на воркер, не на зрителя) и раздаёт сообщение своим
WebSocket-клиентам. Pub/Sub не хранит историю: кто не подписан в момент
публикации — не получит сообщение. Для живой ленты это нормально.

## Процессная модель backend

```bash
gunicorn app.main:app \
  --worker-class uvicorn_worker.UvicornWorker \
  --bind 0.0.0.0:8000 \
  --timeout 90 \
  --graceful-timeout 30
```

- **Gunicorn** — мастер-процесс: слушает порт, запускает воркеры, перезапускает
  упавшие, координирует graceful reload и shutdown.
- **UvicornWorker** даёт каждому воркеру свой asyncio event loop — на нём работают
  `async def`/`await`, в том числе ожидание результата из пула процессов.
  (Класс живёт в пакете `uvicorn-worker`: модуль `uvicorn.workers` объявлен
  устаревшим.)
- **Число воркеров не хардкодится** флагом `--workers`: gunicorn сам читает
  `WEB_CONCURRENCY`. В Dockerfile дефолт `2`, compose переопределяет под машину.
- **`COMPUTE_POOL_SIZE`** (дефолт 1) — сколько процессов в `ProcessPoolExecutor`
  у каждого воркера. Читается в `app/config.py`.
- **Почему ProcessPoolExecutor, а не потоки**: fibonacci — чистый CPU на Python-
  байткоде, а его в одном процессе исполняет только один поток за раз (GIL). Поток
  с вычислением отнимал бы GIL у event loop, и воркер «подвисал» бы; два вычисления
  в потоках шли бы по очереди. У процесса свой GIL и своё ядро.
- **`--graceful-timeout 30`**: на **SIGTERM** (вежливая просьба, её можно обработать)
  воркеры перестают принимать новые запросы и 30 с дорабатывают текущие, потом
  мастер их убивает. **SIGKILL** обработать нельзя — процесс умирает мгновенно.
  Поэтому в compose `stop_grace_period: 40s` (больше 30 с), иначе Docker пришлёт
  SIGKILL раньше. Порог на N гарантирует, что вычисление укладывается в это окно.

### Правило ёмкости

```
одновременно считающих процессов = реплики × WEB_CONCURRENCY × COMPUTE_POOL_SIZE ≈ ядра
```

Uvicorn-воркеры лёгкие — в основном ждут Redis и результат вычисления. CPU грузят
процессы пула. Поэтому число воркеров и размер пула — разные параметры, но их
произведение (вместе с числом реплик) ограничивает суммарную вычислительную нагрузку.
Если процессов больше, чем ядер, они просто делят ядра и каждый считает медленнее.

| Окружение | Реплики | WEB_CONCURRENCY | COMPUTE_POOL_SIZE | Итого |
|---|---|---|---|---|
| Локально, 4 ядра | 2 | 2 | 1 | 4 |
| Сервер, 2 ядра | 2 | 1 | 1 | 2 |

## Запуск

```bash
cp .env.example .env            # опционально: переопределить MAX_FIBONACCI_N и т.п.
docker compose up --build --scale backend=2
```

Открыть https://localhost/ — браузер предупредит о self-signed сертификате, это
ожидаемо («Дополнительно → Перейти»).

> Масштабируй **всегда** с `--scale`: `docker compose up -d` без него вернёт backend
> к одной реплике. Перезапускать nginx после изменения числа реплик не нужно: он
> перечитывает их адреса через Docker DNS каждые 5 с (`resolve` в upstream).

Тесты (нужен запущенный Docker — Testcontainers поднимает настоящий Redis):

```bash
python -m venv .venv && .venv/bin/pip install -r backend/requirements.txt -r requirements-dev.txt
ruff check backend
cd backend && python -m pytest -q
```

## Docker: ключевые решения

- **Multi-stage Dockerfile**: зависимости ставятся в стадии `builder` в venv, в
  финальный образ копируется только готовый venv и код — без кэша pip и
  инструментов сборки.
- **Non-root**: процесс работает под пользователем `app` (uid 10001), код
  принадлежит root и только читается. Принцип минимальных привилегий: уязвимость в
  приложении даёт атакующему права `app`, а не root.
- **HEALTHCHECK в Dockerfile**: без него Docker видит только «процесс жив/не жив».
  Gunicorn-мастер может жить, когда приложение не отвечает или не видит Redis. С
  проверкой контейнер становится `healthy/unhealthy`, и на это опирается
  `depends_on: condition: service_healthy`.
- **`restart: unless-stopped`, а не `always`**: оба перезапускают упавший контейнер
  и поднимают его после рестарта Docker. Разница — если контейнер остановили
  **намеренно** (`docker compose stop`): `always` поднимет его снова после рестарта
  Docker-демона или сервера, `unless-stopped` — оставит остановленным. Ручная
  остановка остаётся в силе.
- **Лимит логов** (`json-file`, `max-size: 10m`, `max-file: 3`): иначе JSON-логи
  растут без предела и однажды забивают диск.
- **Нет `container_name` у backend** — с фиксированным именем `--scale` невозможен.

## Nginx: что делает каждый блок

| Блок | Зачем |
|---|---|
| `upstream backend { least_conn; zone; server backend:8000 resolve max_fails=3 fail_timeout=5s; keepalive; }` | Docker DNS отдаёт адреса всех реплик. `least_conn` — запрос уходит туда, где меньше активных соединений: запросы сильно разные по длительности (fib(10) мгновенно, fib(35) — секунды), round-robin мог бы отправить новый запрос на занятую реплику. `zone` — счётчики в общей памяти всех worker-процессов nginx, иначе у каждого worker'а своя картина. `resolve` + `resolver 127.0.0.11 valid=5s`: адреса реплик перечитываются по ходу работы, новые и пересозданные реплики подхватываются без перезапуска nginx. `keepalive 32` + `keepalive_timeout 60s`: постоянные соединения к backend вместо нового TCP на каждый запрос (у gunicorn `--keep-alive 75` — дольше, чтобы закрывал nginx). `max_fails=3 fail_timeout=5s`: реплика выключается после 3 ошибок за 5 с, а не после одной (по умолчанию), иначе случайные обрывы под нагрузкой выключали обе реплики. |
| `log_format upstream_log ... upstream=$upstream_addr` | В логе nginx видно, какая реплика обработала каждый запрос. |
| `limit_req_zone api_limit` (20 r/m) и `api_light` (10 r/s), `limit_req_status 429` | Первый, грубый слой rate limit: отсекает агрессивных клиентов до Python и Redis. Второй слой — точный, в приложении через Redis (5 вычислений/мин). Defense in depth: два слоя разной строгости, а не дублирование. |
| `server :80` | `/nginx-health` для Docker healthcheck (до редиректа), всё остальное — 301 на HTTPS. |
| `server :443`, `ssl_*` | TLS termination (см. ниже). Сертификат self-signed, генерируется при **старте** контейнера — чтобы закрытый ключ не попал в слой публичного образа. |
| `gzip`, `add_header X-Content-Type-Options / X-Frame-Options / Referrer-Policy` | Сжатие текстовых ответов и базовые security-заголовки. Заголовки повторены в location для статики: `add_header` в location отменяет унаследованные. |
| `location /` + `try_files` | Статика напрямую с диска — работает даже при мёртвом backend. |
| `location = /api/compute` | Строгий лимит, `client_max_body_size 1k` (принимаем только крошечный JSON), `X-Real-IP`, таймаут 90 с. |
| `location /api/` | Остальной API (health, instance-info) с мягким лимитом. |
| `location /ws` → `upstream backend_ws` | WebSocket: `proxy_http_version 1.1` + `Upgrade`/`Connection`, таймаут 1 ч. Отдельный upstream (те же реплики, свои счётчики): иначе открытая вкладка с лентой — это «вечное» активное соединение, и `least_conn` отправлял бы все API-запросы на соседнюю реплику. |

### TLS termination vs end-to-end

Здесь **TLS termination на nginx**: снаружи трафик зашифрован до nginx, а дальше,
внутри приватной Docker-сети, до backend идёт обычный HTTP. Плюсы: сертификаты в
одном месте, backend не тратит CPU на TLS. Граница доверия — Docker-сеть.
**End-to-end** шифрование означало бы, что и участок nginx → backend идёт по TLS
(у backend свой сертификат) — нужно, когда внутренней сети не доверяют (общая
инфраструктура, требования compliance).

## Как проверить

Все команды — из корня проекта при запущенном стеке
(`docker compose up --build --scale backend=2 -d`).

> Лимит приложения — 5 вычислений в минуту с IP. Если проверки идут подряд, между
> ними подожди минуту или сбрось счётчики:
> `docker compose exec redis sh -c "redis-cli --scan --pattern 'ratelimit:*' | xargs -r redis-cli del"`.
> А чтобы fibonacci(35) снова реально считался, а не брался из кэша:
> `docker compose exec redis sh -c "redis-cli --scan --pattern 'compute:cache:*' | xargs -r redis-cli del"`.

**1. Cache stampede protection — самое интересное для демонстрации:**
```bash
# Отправляем ОДИНАКОВЫЙ дорогой запрос (например, fibonacci(35))
# ОДНОВРЕМЕННО, 5 раз параллельно
for i in 1 2 3 4 5; do
  (curl -s -X POST https://localhost/api/compute \
    -k -H "Content-Type: application/json" \
    -d '{"input": 35}' &)
done
wait
# Проверь логи backend'ов: РЕАЛЬНОЕ вычисление должно произойти
# ТОЛЬКО ОДИН раз, остальные 4 запроса должны получить результат
# из кэша/дождавшись лока, а не запускать fibonacci(35) параллельно
# 5 раз (что было бы дорого и бессмысленно)
```
Логи: `docker compose logs backend | grep '"input": 35' | grep -E 'compute_started|lock_wait|cache_hit'`
— `compute_started` ровно один, а `lock_wait` встречается у ОБЕИХ реплик: лок общий
для контейнеров. Нюанс команды: `wait` здесь ничего не ждёт — `( curl … &)` запускает
curl в подоболочке, которая тут же завершается, у текущего shell фоновых задач нет.
Ответы допечатаются через ~1 с после возврата приглашения.

**2. Event loop не блокируется во время тяжёлого вычисления:**
```bash
# Запусти тяжёлое вычисление в фоне
curl -k -X POST https://localhost/api/compute \
  -d '{"input": 35}' &

# СРАЗУ ЖЕ, пока предыдущее ещё считается — health check
curl -k https://localhost/api/health
# Должен ответить МГНОВЕННО, а не ждать, пока фибоначчи досчитается —
# доказательство, что ProcessPoolExecutor не блокирует event loop
```
С несколькими репликами эта проверка **слабая**: `least_conn` отправит health на
свободную реплику, и даже внутри реплики он может попасть в соседний воркер.
Строгий вариант — отдельный контейнер с ОДНИМ воркером, оба запроса в него:
```bash
docker compose run -d --name probe -e WEB_CONCURRENCY=1 backend
sleep 15   # ждём healthy
docker exec probe sh -c '
  curl -s -X POST localhost:8000/api/compute -d "{\"input\": 35}" -w " <- compute %{time_total}s\n" &
  sleep 0.2
  curl -s localhost:8000/api/debug/instance-info -w " <- %{time_total}s\n"
  wait'
docker rm -f probe
# instance-info отвечает за ~1 мс с тем же pid и "pending_computations": 1 —
# этот самый воркер прямо сейчас ждёт fib(35), но его event loop свободен.
```

**3. Горизонтальный скейлинг — запросы реально распределяются:**
```bash
docker compose up --build --scale backend=2 -d
for i in $(seq 1 10); do
  curl -sk https://localhost/api/debug/instance-info
  echo ""
done
# Должны увидеть РАЗНЫЕ hostname (разные контейнеры) в ответах
```
Там же в логах nginx: `docker compose logs nginx | grep -o 'upstream=[0-9.:]*' | sort | uniq -c`.

**4. Статика отдаётся без backend:**
```bash
docker compose stop backend
curl -Ik https://localhost/
# 200 OK, несмотря на мёртвый backend
```
API в это время отвечает 504 примерно через 10 с: адреса остановленных контейнеров
молчат, и nginx ждёт `proxy_connect_timeout 5s` на каждую из двух реплик.
Вернуть: `docker compose up -d --scale backend=2`.

**5. Rate limit общий между всеми репликами:**
```bash
for i in $(seq 1 20); do
  curl -sk -X POST https://localhost/api/compute \
    -d '{"input": 30}' -o /dev/null -w "%{http_code}\n"
done
# 429 должен появиться около 6-го запроса, а не после 15-го
# (5 лимит × 3 реплики, если бы лимит был не общим)
```

**6. Порог на N срабатывает на сервере:**
```bash
curl -sk -X POST https://localhost/api/compute \
  -H "Content-Type: application/json" -d '{"input": 50}' -w "\n%{http_code}\n"
# Ожидаем 422 сразу же, а не зависший запрос и 100% CPU.
# (Порог по умолчанию — 35; для экспериментов локально его можно
# поднять переменной MAX_FIBONACCI_N, но на публичном сервере — нет.)
```

**7. Не больше одного дорогого вычисления на IP одновременно:**
```bash
curl -sk -X POST https://localhost/api/compute -d '{"input": 35}' -o /dev/null &
sleep 0.5
curl -sk -X POST https://localhost/api/compute -d '{"input": 34}' -o /dev/null -w "%{http_code}\n"
# Второй запрос (другой input, значит другого лока нет) должен получить 429
wait
```

**8. Graceful shutdown посреди вычисления** (не из списка, но требование SPEC):
```bash
docker exec computing_service-backend-1 curl -s -X POST localhost:8000/api/compute \
  -d '{"input": 35}' -w " <- HTTP %{http_code}\n" &
sleep 0.3
docker stop computing_service-backend-1
wait
# Ожидаем HTTP 200: SIGTERM -> gunicorn перестаёт принимать новые запросы, воркер
# дожидается текущего (в логах compute_finished раньше worker_stopped), контейнер
# выходит с кодом 0 примерно за секунду — не дожидаясь 30-40 с таймаутов.
docker compose up -d --scale backend=2
```

## Нагрузочный тест: 100 клиентов одновременно

С одной машины все запросы для nginx приходят с одного IP, и лимиты по IP срежут
всё после 5-го. Поэтому на время теста nginx доверяет `X-Forwarded-For` **только из
Docker-сети** (`loadtest/realip.conf`, модуль realip), а генератор нагрузки
работает внутри этой сети и даёт каждому клиенту свой адрес.

```bash
# включить тестовый режим nginx
docker compose -f docker-compose.yml -f loadtest/docker-compose.loadtest.yml up -d --scale backend=2
# 100 клиентов, у каждого случайное N из 20..35
docker run --rm -i --network computing_service_default computing_service-backend \
  python - --clients 100 --min-n 20 --max-n 35 < loadtest/loadtest.py
# 100 клиентов с ОДИНАКОВЫМ N=35 — stampede в масштабе
docker run --rm -i --network computing_service_default computing_service-backend \
  python - --clients 100 --min-n 35 --max-n 35 < loadtest/loadtest.py
# ОБЯЗАТЕЛЬНО вернуть обычный режим (иначе любой может назваться любым IP)
docker compose up -d --scale backend=2
```

Флаг `--retries 5` включает повторы по той же логике, что во фронтенде. Размер
очереди меняется без правки кода: `BACKPRESSURE_FACTOR=1 docker compose ... up -d`
(1 = очереди нет, только считающиеся задачи).

Что получилось на 4 ядрах (2 реплики × 2 воркера × пул 1), 100 клиентов:

| Сценарий | 200 | 503 | p95 | max | Лишних запросов |
|---|---|---|---|---|---|
| 16 разных N, **без очереди**, без повторов | 69 | 31 | 0,80 с | 0,91 с | — |
| 16 разных N, **без очереди**, с повторами | 100 | 0 | 3,50 с | 3,65 с | 48 |
| 16 разных N, **очередь на сервере** (по умолчанию) | **100** | **0** | **0,91 с** | **1,92 с** | **0** |
| одно N=35, очередь | 100 | 0 | 1,28 с | 1,29 с | 0 |
| **1000** клиентов, 16 разных N | 1000 | 0 | 1,24 с | 1,81 с | 0 |
| **1000** клиентов, одно N=35 | 1000 | 0 | 1,50 с | 1,58 с | 0 |

С порогом **N=38** (fib(38) = 4,35 с в контейнере, `BACKPRESSURE_FACTOR=3`, чтобы
(3−1) × 4,35 с < 10 с ожидания в очереди), 1000 клиентов:

| Сценарий | Итог |
|---|---|
| одно N=38 | 1000 × 200, посчитано 1 раз, max 4,97 с |
| 5 тяжёлых N (34..38) | 1000 × 200, пятое вычисление 3,1 с ждало слот в очереди, max 7,3 с |
| 19 разных N (20..38), без повторов | 982 × 200, **18 × 503 `overloaded`** — мест 4 воркера × 3 = 12, а разных тяжёлых вычислений пришло 19; отказ мгновенный (0,04 с) |
| то же, с повторами как во фронтенде | **1000 × 200**, 58 клиентам понадобилась 2-я попытка, max 5,4 с |

Под нагрузкой вычисления на ~10% медленнее, чем в одиночку (fib(38): 4,9 с против
4,35 с) — 4 процесса делят ядра виртуальной машины Docker.

Строка «1000 клиентов, одно N=35» до исправлений давала **493 × 500 и 14 × 502**: обычный пул Redis
падал при исчерпании, а nginx с `max_fails=1` после пары ошибок выключал обе
реплики («no live upstreams»). Сейчас — блокирующий пул, уведомления вместо опроса
(команд Redis за прогон втрое меньше) и `max_fails=3 fail_timeout=5s`.

Во всех сценариях реально посчитано ровно столько, сколько разных N (16 и 1):
остальные ответы — после ожидания лока. Очередь на сервере вдвое сокращает «хвост»
задержки по сравнению с повторами: место отдаётся сразу, как освободилось, а не
через `Retry-After` + случайная пауза.
